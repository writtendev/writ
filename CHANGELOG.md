## [Unreleased]

### Fixed
- `spec/testdata/anchors/invalid/index.json`'s 8 `kind: "invariant"` vectors and `spec/testdata/schema-ops/invalid/index.json`'s 5 `rejects: "invariant"` vectors were each held to an aggregate disjunction (`anchorInvariants`, `spec.ValidateFieldRule` via `schemaOpsInvariants`): a vector passed as long as *any* rule in the aggregate rejected it, not necessarily the one its `reason` named, so the harness could not tell a correctly-pinned vector from a coincidentally-passing one (the same trap WRIT-292 closed for person vectors). Both corpora now name the specific rule each vector pins in a sibling `invariant_rule` field, and the harness holds each vector to exactly that rule: named rule rejects, every other rule in scope accepts, and a coverage check fails if a rule has no vector naming it. Anchors decomposes into six independently-callable rules in `spec/anchors_test.go` (a pure test change); schema-ops required production code, since the aggregate is `spec.ValidateFieldRule` itself, so each of its 20 violation branches now wraps an unexported sentinel error with `%w`, re-exported to `spec_test` as `FieldRuleSentinels`, and `spec/fieldrules_test.go`'s substring assertions became sentinel-identity checks. `spec.ValidateFieldRule`'s error text gained a `: invariant <token>` suffix as a result, which golden and schemasrc invalid-corpus fixtures captured verbatim and are updated to match (behavior otherwise unchanged; every non-test caller only formats the error). Six of `ValidateFieldRule`'s invariants are reachable from a schema-valid `define-field` body but have no conformance vector; `spec/schema_ops_test.go` now declares them, plus the rest of the twenty sentinels no vector can reach, in an explicit inventory checked against both the corpus and `spec/fieldrules_test.go`'s own unit coverage, so the gap is visible in code rather than assumed closed -- minting those six vectors is deferred to a follow-up. Also folds in the accepting side of the same class of gap: `TestValidPersonVectors` now checks every valid person vector against `spec.PersonValueRepertoireOK` as well as `spec.PersonValueIsStreamSafe`. `spec/anchors.md`, `spec/schema-ops.md`, and `spec/README.md` document `invariant_rule` alongside `kind`/`rejects` (WRIT-306); `spec/anchors.md` and `spec/schema-ops.md` also each now name, in descriptive prose, the token vocabulary their respective cross-field rules and `ValidateFieldRule`'s error suffix draw from, since neither was documented anywhere a maintainer or schema author could look it up.
- `internal/projection`'s `columnValue` stored a folded value that contradicts its target's declared `value_type` (e.g. a `count int lww` field written `{"count":"abc"}` by a foreign or buggy writer bypassing producer validation) as SQL NULL, silently: the two read surfaces disagreed, since `state.Fold` kept the value verbatim per `spec/fold.md` §7.1, and a drop-and-rebuild reproduced the NULL. The three type-mismatch fallthroughs in `columnValue` (`int`, `number`, `bool`) now store the value as text instead, matching what a genuinely untyped column already does; NULL is reserved for a value's actual absence. `spec/value-types.md` no longer claims a reader routes such a value through the `UnknownOp` channel — that channel is for unrecognized ops and fields, not this case — and points at `spec/fold.md` §7.1 instead, where the true reader rule already lives. One residual: SQLite's `INTEGER`/`REAL` column affinity still converts a numeric-looking string (`"42"` into an `int` column reads back as the number `42`, not the string), so the two surfaces can still disagree on type for that narrow case, though never again on presence.
- `spec/identifiers.md` §Reference grammar and §Object homing read as though a repository designator named one logical repository, but WRIT-300 (`a92c309`) made minting per-clone: a clone that runs `writ init` mints its own designator rather than inheriting the source repository's, so a repository's initialized clones are separate repositories that each carry their own designator, and no single designator covers all of them. The prose is narrowed to match: §Object homing keeps its existing MUST verbatim and gains a sentence stating that consequence, pointing back at §Repository designators for the minting mechanism rather than restating it, and §Reference grammar's fully-qualified row drops the definite article and gains a note that a designator identifies a repository as a participant knows it, not a logical repository globally. Deliberately descriptive, not a new rule: the spec still does not say which participant's designator a qualified reference carries, and nothing in writ dereferences one — settling that would be a separate normative change needing its own conformance fixtures, not a prose edit.
- `cmd/writ/schema.go`'s `schemaNamespaces` counted a folded schema object toward `writ schema apply`'s porcelain namespace count and its `--json` `namespaces` field as soon as the object's id was the derived form of its own namespace (WRIT-254's gate) — without also checking that the namespace itself satisfies `spec/schema-ops.md` §2's bare-form grammar (WRIT-253's gate), the other half of the two whole-object drop gates `engine/schema.go`'s `resolveSchemaTypes` applies before installing anything for a schema object. A namespace that is legal printable ASCII but grammar-invalid (e.g. object id `schema:Ev!l';--`) survived the derived-id check alone and was reported as declared, even though the resolver drops the whole object and installs nothing for it (WRIT-291). `schemaNamespaces` and `resolveSchemaTarget` now both gate on a single `internal/state.SchemaInstallable` predicate — factored out of `resolveSchemaTypes`'s exact drop conjunction — so the CLI's report can no longer disagree with what the reader actually holds. Nothing about what the engine folds or installs changed; this is a CLI-report fix only.
- `engine/api_test.go`'s `TestAPIShapeNoGitInternalsLeak` guard was partly vacuous (WRIT-298): `forbiddenPackagePrefixes`' full-path entries (`.../internal/dag.`, `.../internal/identity.`, `.../internal/sync.`) never matched anything — the values under test carry a `PkgPath` with no trailing dot — so only the short-name entries (`plumbing.`, `object.`, `storer.`) were ever doing any work, and the test had always passed regardless. Matching is now a single `PkgPath`-only rule (`pkgPath == forbidden || strings.HasPrefix(pkgPath, forbidden+"/")`), so the short-name entries are dropped as redundant with the `github.com/go-git/go-git` module prefix they duplicated: `assertNoGitLeak` recurses through a map's key and value, and through a named pointer/slice/array/chan's own element after checking the container itself, so a forbidden type is still reached whether it sits directly on a field, behind a map, or behind a writ-named composite (e.g. `type Sigs []object.Signature`); `checkType`'s own field-recursion switch gains the same `chan` case, so a forbidden type behind a channel field is reached the same way as one behind a pointer, slice, array, or map. `checkType`'s `NumMethod` loop reaches a method's parameter and result types the same way for a concrete type and an interface, so a forbidden type behind a method signature or an interface's method set is caught alongside a plain field, a map, or a writ-named composite. Repairing the matching made `internal/dag.` fire on intentional API — `writ.RefreshStats.Rejections` is `[]dag.Rejection` — so it comes off the list; `writ.Rejection` and `writ.RejectReason` (below) make that exposure a root-package one instead. `internal/identity` and `internal/sync` stay listed and are still honestly clean (zero hits). A new `TestAPILeakGuardBites` proves the guard fires — a go-git type on a plain field, one behind a map reached only by `checkType`'s own map recursion, one behind a map reached only by `assertNoGitLeak`'s own map recursion (two separate fixtures, since a single `map[string]plumbing.Hash` case is rescued by either recursion alone through `plumbing.Hash`'s value-receiver methods and so pins neither independently), one behind a writ-named composite, plus a negative case pinning `writ.RefreshStats{}` at zero findings — since a green run against a corrected list proves nothing on its own, which is the entire reason this guard was found to be vacuous in the first place.
- `spec/identifiers.md` §Storage and discovery specified a config key (`writ.repo-id`) that `internal/identity/repoid.go` never wrote or read -- the engine has always used `writ.repoId` -- and a `refs/writ/meta/repo-id` ref carrier that `spec/ref-layout.md`'s own §Ref naming grammar forbids (`meta` is not a 16-hex writer-id) and that no code reads (WRIT-300). The spec is amended to match the engine rather than the engine changed to match the spec: the config key becomes `writ.repoId`, matching the sibling `writ.writerId`/`writ.personId` spelling, and the ref carrier is deleted outright rather than implemented. Review then surfaced a second, genuine engine defect along the way, and the ticket was widened to carry it rather than ship a spec contradicting the implementation it was filed to correct: `EnsureRepoID`/`LoadRepoID` read `writ.repoId` out of *merged* git config (local, then global, the same helper `writ.writerId`/`writ.personId` use), so a `writ.repoId` set in a user's global `~/.gitconfig` was silently adopted by every repository on the machine, with no local key ever written -- two repositories then shared one designator and `<repo-id>#<object-id>` stopped disambiguating anything. Global sourcing is correct for `writerId`/`personId` (one identity across a person's repositories is the point); a repo-id has the opposite requirement, since its whole job is telling repositories apart. `internal/identity/repoid.go`'s `LoadRepoID` and `EnsureRepoID` now read `writ.repoId` from local repository configuration only (a new `readLocalGitConfig`, `git config --list --null --local`); `writerId` and `personId` are untouched. `spec/identifiers.md` §Storage and discovery now states local-only sourcing to match, and the immutability paragraph's clone sentence is corrected in the same commit: a clone mints its own designator not only because it does not inherit the source repository's local config, but because no other config scope is consulted for this key either. No conformance fixture, JSON schema, or `spec/*_test.go` pinned the old config key, the ref carrier, or the merged-config read.
- `writ sync <remote>` (`internal/sync`) had three argv/config-hygiene defects (WRIT-283). First, and most seriously, a real argument-injection hole: `writ sync -- --upload-pack=<script>` passed the remote positionally to `git fetch`/`git push`, so a `-`-leading remote name was parsed as a flag and, in the `--upload-pack` case, verified to **execute an attacker-controlled script**. Every `git fetch`/`push`/`config` call in `internal/sync` now passes `--end-of-options` ahead of its positionals, and a new `ValidateRemoteName` additionally rejects an empty, `-`-leading, or otherwise refname-invalid name outright (exit 2, usage error -- an empty name, e.g. from an unset `$REMOTE` in a script, is a usage error like any other malformed one, not the exit 1 a caller reads as a transport failure and retries) before it ever reaches a subprocess -- a `/`-containing name (e.g. `team/fork`) is deliberately accepted, since git itself accepts such remote names and an earlier, stricter rule stranded ops on remotes git fully supports. Second, `Store.Sync` and `writ init` (both funnel through `internal/sync.Client.Ensure`) called `git config --add remote.<remote>.fetch ...` before confirming the remote existed at all: `writ sync nosuchremote` and `writ init nosuchremote` each left a url-less `[remote "nosuchremote"]` fetch-only section behind, and a malformed name (e.g. `"a b"`) wrote an invalid refspec that made every subsequent plain `git remote` in the repository exit 128 -- a self-inflicted denial of service recoverable only by hand-editing `.git/config`. `Ensure` now confirms `remote.<remote>.url` **or** `remote.<remote>.pushurl` is configured (a new `RemoteConfigured` probe) before writing anything -- a push-only remote is real, git-supported configuration (`git remote` lists it, `git push` works against it), and probing `url` alone made such a remote read as nonexistent and stranded ops it could otherwise still push, and `Store.Sync` runs the same name-validation-and-existence check once, upfront, ahead of `Ensure`, `Fetch`, and `Push` (a remote that does not exist at all is not a fetch failure WRIT-270's "push is never gated on fetch" needs to tolerate -- there is nowhere to push either). A well-formed but unconfigured remote name keeps exit 3's existing meaning unchanged; only the newly-rejected malformed-name case is exit 2. `writ init` (with no remote argument, one call per remote `git remote` lists) used to abort its whole run the moment `Ensure` rejected any one of them this way -- and `git remote` lists a url-less `[remote "x"]` section (e.g. from a global `remote.<name>.prune`) or a `-`-leading name exactly as happily as a good remote, so a config key nobody asked writ to touch could leave every *other*, perfectly good remote unconfigured too. `writ init` now configures every discovered remote it can and reports the ones it skipped and why, rather than stopping part-way -- and does not split its exit code on which of the two ways Ensure's gate rejected one (a url-less section, `ErrUnknownRemote`, or an invalid name, `ErrInvalidRemoteName`): a remote writ merely discovered being unusable is not a failure of the run, so both are reported on stderr and skipped with no remedy printed -- writ was never asked to touch that remote in the first place -- and the run still exits 0. Naming a remote explicitly on the command line is unchanged -- a bad name typed there still stops the run, exit 1. Third, exit 5 ("not a git repository / store cannot be opened", `docs/cli-json.md` §2.5) was `sync`-only: `writ object list --json`, `writ schema show --json`, and every other verb returned exit 1 for the same failure, so a machine consumer could not distinguish "no repo" from a transport failure. `cmd/writ/store.go`'s `renderErr` (shared by every verb) now maps `writ.ErrStoreOpen`/`writ.ErrNotRepository` to exit 5 directly, and `cmd/writ/sync.go`'s `exitCodeFor` reuses that same classification so the two cannot drift.
- `opMatchesRule` (`internal/fold/fold.go`, mirrored in `spec/reffold.go` and the projection's own `opMatchesRuleLite`) treated a zero `op_version` or an empty `object_type` on the *op* side as a wildcard alongside the rule side (WRIT-275). The op-envelope schema requires `op_version >= 1` and a non-empty `object_type` on every op that reaches the log, so that half of the wildcard was unreachable through the log and existed only for a hand-built op fed straight to the public `writ.Fold`, where it let two same-target accumulators consume one op that should have matched at most one of them. The rule-side wildcard (a caller-supplied rule table legitimately omitting either) is unchanged. `spec/fold.md` §5 now scopes both wildcards to the rule only; a new merge vector, `op-version-zero-does-not-match-scoped-rule.json`, pins the removal across the reference fold and the engine.
- `internal/codec/sshsig/allowedsigners.go` matched an op's signing principal against an `allowed_signers` line, and the signature's `namespaces=` option against the signed namespace, with `strings.EqualFold` and a lowercased `path.Match` (WRIT-278), so an op authored `Alice@Example.COM` verified as `valid` against an `alice@example.com` line, or `namespaces="Git"` matched namespace `"git"`, where OpenSSH's `sshsig_check_allowed_keys` — which calls `match_pattern_list(x, list, 0)`, `dolower=0` — rejects both: a live writ-says-`valid` / OpenSSH-says-`wrong-key` divergence on the exact outcome vocabulary `spec/signing.md` makes normative, not merely a stricter-than-OpenSSH quirk. `matchPattern` and `matchNamespace` now compare principal and namespace case-sensitively (`==` and un-lowercased `path.Match`), matching OpenSSH exactly on case while leaving `path.Match`'s other, pre-existing divergences from `match_pattern` (`*` crossing `/`, `[...]` classes, `\` escapes) and `matchNamespace`'s lack of globbing/`!` negation as separate, already-tracked gaps. A new `bad-sig-principal-case` fixture commit (`envelope-bad-signatures`, authored by a new fixture identity, `alice_upper`, reusing Alice's key) pins `wrong-key` for a case-mismatched principal. Engine-only: all three changed comparisons are inside unexported helpers, so `api/engine.txt` does not move.
- `internal/codec/sshsig/allowedsigners.go`'s `matchPattern` used Go's `path.Match`, and `matchNamespace` supported neither globbing nor `!` negation — the two divergences WRIT-278 above found and deliberately deferred as "would turn a three-line fix into a rewrite of the matcher" (WRIT-302). `path.Match` disagrees with OpenSSH's `match_pattern` in both directions: over-permissive, since it parses `[...]` as a character class and `\` as an escape (`ali[cd]e@*.test` and `alice\@*.test` both wrongly authorize `alice@example.test`), and under-permissive, since its `*` will not cross a `/` (`*@example.test` wrongly rejects `alice/laptop@example.test`) and an unbalanced `[` returns `ErrBadPattern`, silently treated as no-match rather than the literal byte OpenSSH takes it as. `matchNamespace`'s exact-or-bare-`*` check meant a `namespaces="g*"` option never matched (under-permissive) and a `namespaces="!git,*"` option ignored the negation and matched anyway (over-permissive). `spec/signing.md`'s "Trust Store and Principal Validation" section now states the matching rule normatively on its own terms rather than by OpenSSH revision — including that a run of two or more trailing `*` matches even after the rest of the subpattern has already exhausted the value (`alice@example.test**` matches `alice@example.test`), the one class where the NFA `match.c` has shipped since rev 1.46 disagrees with the older recursive matcher (this is never a `path.Match` divergence: `path.Match` itself gets this class right, and so did the pre-PR `matchPattern` that called it). The trailing-`*`-run rule is pinned at the unit layer (`TestAllowedSigners_TrailingStarRun`), since CI's own OpenSSH 9.x interop oracle still runs the pre-1.46 recursive matcher and cannot exercise it. `spec/signing.md` also states that OpenSSH's 1023-byte-or-more subpattern abort (which discards even an already-recorded match from an earlier subpattern in the same list) is a `match.c` buffer artifact conforming verifiers MUST NOT replicate, pinned by `TestAllowedSigners_OpenSSHMatchSemantics`'s long-subpattern cases. `path.Match` is replaced with a direct byte-wise port of `match.c`'s `match_pattern`/`match_pattern_list`, run identically over both lists; `matchPrincipal` and `matchNamespace` are now both one-line callers of the same `matchPatternList`. This supersedes WRIT-278's "leave the other `path.Match` divergences as tracked gaps" sentence: the divergences it deferred are closed here, not bridged. A new `envelope-signer-patterns` fixture (via a new `trust_store:` description knob, `spec/fixtures/description.go`/`allowedsigners.go`, since the generated default trust store only ever emits a bare literal principal) pins six cases as golden `verification_outcome` flips (two of the six, the bracket-class and backslash-literal cases, share one underlying scenario and are decided jointly rather than each by its own rule — see the fixture description), and `internal/codec/interop_test.go`'s `ssh-keygen -Y verify` cross-check gains a seventh (byte-wise vs. rune-wise `?`). Engine-only: every changed function is unexported, so `api/engine.txt` does not move.
- The person identifier value repertoire (spec/identifiers.md §Value character repertoire, `internal/textsafe.Forbidden`) missed U+061C ARABIC LETTER MARK, U+2060 WORD JOINER and the rest of U+2061-2064, U+00AD SOFT HYPHEN, U+180E, and the U+E0000-E007F tag block, so a person-ref carrying one of them reached a terminal or `--json` output with a live invisible or bidi-control character intact -- defeating the "visually identical, compares unequal" spoofing guarantee WRIT-137 exists to close (WRIT-276). The forbidden set widens from the old hand list to General_Category `Cc` union `Cf` at Unicode 17.0.0, plus four named `Default_Ignorable_Code_Point` code points that render invisible but are not `Cf` (U+115F, U+1160, U+3164, U+FFA0 -- Matt's ruling on the ticket), closing the remaining invisible-character gap a `Cc union Cf`-only rule would still leave open. The person-id JSON Schema pattern widens to match everywhere the new range fits in the Basic Multilingual Plane; the tag block and a handful of other supplementary-plane `Cf` ranges cannot be expressed in an ECMA-262 character class without the `u` flag (a range spanning a surrogate pair parses as a reversed range) and stay producer-enforced only. `textsafe.EscapeForbidden`'s escape form changes for a code point above the Basic Multilingual Plane: it now emits the UTF-16 surrogate pair (`\uXXXX\uXXXX`) rather than assuming every forbidden code point fits in one `\uXXXX`, so the escaped text stays valid, losslessly-decodable JSON. No fold change: the repertoire rule stays producer-side hygiene, never consulted by the fold.
- A single peer force-pushing a rewind of their own chain (a backup restore, an unpushed-history rebase, or a plain `--force`) made every other writer's `writ sync` fail non-fast-forward on every retry, exit 4, "1 op unsynced" -- and the rewinding peer's own unrelated ops could never reach the remote either, recoverable only by raw `git fetch`/`update-ref` plumbing (WRIT-270). No hostile actor was required. The root cause was `internal/sync/refspec.go`'s fetch refspec deliberately omitting the leading `+`, on the theory that a rejected non-fast-forward was safer than silently rewriting history; that theory didn't survive contact with the projection's actual behavior, which already tolerates a `Rewound` chain and rebuilds (`internal/projection/refresh.go`), so the safety the omission bought was safety the projection layer provides anyway on every fetch. `FetchRefspec` now returns `+refs/writ/*:refs/remotes/<remote>/writ/*`; a rewind lands instead of being rejected, and `dag.EnumerateSince` reporting `Rewound` now runs in the normal case rather than never. Push is also no longer gated on fetch (or refspec-`Ensure`) succeeding (`engine/sync.go`): `PushRefspec` is constructed per invocation and passed on the command line, never read from `.git/config`, so a peer's broken chain or a dead remote's fetch failure can no longer strand a different writer's own already-pending ops. Separately, the advice string shown on a push-path non-fast-forward rejection ("fetch latest ops before pushing", `internal/sync/git.go`) was always wrong on that path -- the fetch had already succeeded -- and now names the real cause: something wrote into this writer's own namespace, or the remote was restored/rewound, and fetching will not fix either. `RefspecState`'s `StatusForced` is renamed to `StatusUnforced`, inverting its meaning: a non-forced refspec is now the drift state `Ensure` repairs (an old clone's `.git/config` still carries the pre-WRIT-270 unforced form), which is a **breaking change to `api/engine.txt`**, expected and accepted before v0.1.0. `spec/ref-layout.md`'s "pushes cannot non-fast-forward against another writer" claim is corrected -- no git host authenticates per-ref ownership under `refs/writ/*`, so that was never literally true; the spec now states the real property (no other writer's push ever races yours in your own namespace, though your own push can still land non-fast-forward against your own prior push after a restore or rebase) and the trust assumption plainly (anyone with push access is trusted not to write into another writer's namespace, and a forged or overwritten op stays detectable via its signature). The same correction lands in `ARCHITECTURE.md` and `docs/content/why.md`. The accepted cost of the forced fetch is stated in the spec: a rewound peer's ops can silently disappear from this clone's local view of that peer, though anything another writer causally built on them stays reachable from that writer's own chain. `spec/testdata/ref-names/vectors.json`'s pinned fetch refspec moves to the forced form in the same commit as the spec text and the implementation.
- `dag.Store.EnumerateSince`'s incremental walk (Step 3 of `internal/dag/enumerate.go`) stopped expansion only at each chain's own stored cursor tip, so a new op whose causal parent sat deep inside a *different* chain's already-projected history re-walked that whole chain from the causal parent back to its root, even though every one of those commits had already been decoded and folded by an earlier pass (WRIT-273). The normal case is `Objects.Apply`, which causally parents on the target object's current frontier: any object left alone while other objects were created ends up with exactly this shape, so this cost O(history) per `Apply` — twice, since `maybeAutoRefresh` runs before and after. It also corrupted `Stats.Changed`/`Watch` semantics: every re-walked, already-projected object was reported `Changed{Created: true}` again, so `store.Watch` emitted a spurious `EventCreated` for each one instead of the single real `EventChanged`. `EnumerateSince` gains a `WithSeen(match func(opID string) bool) EnumerateOption`: a commit `match` reports true for is treated exactly like a stopBoundary tip — marked visited but neither decoded nor expanded to its parents. `projection.Refresh`'s incremental path supplies it, backed by a prepared point lookup against the `ops` table's `op_id` primary key, so a causal parent already in that table stops the walk instead of re-decoding its ancestry; `rebuildWithConfig`'s cold `EnumerateSince(nil, …)` deliberately never receives it; a rebuild has to be a genuine cold walk or the droppable-cache guarantee (AGENTS.md) breaks. `WithSeen`'s caller invariant — every ancestor of an accepted commit must itself already be recorded by the caller — holds for this projection because `rebuildWithConfig` always truncates `ops` and `chain_tips` together before a cold walk repopulates them, and both a rewound and a disappeared chain force that same full rebuild rather than ever reaching the incremental predicate with a gap. Engine-only, no spec or fixture change: the set of ops a reader ends up holding is identical, only the re-decoding of commits already in the cache goes away — `bounding the walk at non-op commits` (a separate, normative question pinned by the `multi-writer-chains` fixture) is explicitly out of scope and left for a follow-up ticket (WRIT-289).
- Nothing bound a schema object or a namespace to its creator, and both failure modes were irreversible in-band since nothing is ever removed from the log (WRIT-254). **A. Namespace hijack:** `namespace` folds create-once from the first `create` in total order (`internal/state/schema.go`), and a root op's t* is its raw, unbounded `author.When` — so a parentless `create{namespace:"evil"}` on `schema:acme` with a forged, early `author.When` could win create-once outright and rewrite an honest object's namespace out from under it. **B. Permanent object_type contest:** two schema objects binding the same qualified `object_type` withheld rules for it forever, with no tie-break and no tombstone row to delete a schema object by. Ruled (Matt): land options 1+2 together. **1 (`internal/state/schema.go`'s `FoldSchema`, spec/schema-ops.md §3.4):** for the derived-id form (`schema:<namespace>`), a `create` whose body `namespace` disagrees with the id's own suffix — or omits it — is uninterpretable and quarantines into `UnknownOps`, the same shape as the existing `op_version`/`max_length` quarantines; scoped to the derived-id form only, closing A. **2 (`engine/schema.go`'s `resolveSchemaTypes`, spec/schema-ops.md §6 kind 2):** a schema object whose `object_id` disagrees with `"schema:" + its own namespace` is dropped wholesale — before any of its types are even looked at — reported as one conflict per object; `cmd/writ/schema.go`'s `resolveSchemaTarget` applies the same gate when resolving `apply`'s target, so a dropped sibling under the same namespace can never again trigger its old "declared by more than one schema object" refusal (that refusal is now unreachable and is deleted with it). Stated plainly: `resetLocalSchema` drops every local table, so the bump's disclosed cost is that `read_state` and `sync_cursors` are also cleared on first open after upgrading; accepted pre-tag, with no users. `make api-compat` classifies this delta as breaking, which is expected and allowed before v0.1.0 (`AGENTS.md`). Nothing bridges to the old form: a client that wants unpublished notes keeps its own local state; if a real consumer later needs drafts in the engine, it comes back informed by that consumer's needs, as a minor-version addition.
  - **Disclosed coverage loss:** `TestDraftsNeverReachSharedRefs` was the tree's only test asserting that a string a user typed into local-only state never appears in any object reachable from `refs/writ/**`. It cannot be re-grounded on the local state that survives: `ReadState.Mark` takes no free text, and sync cursors carry only a remote, ref name, and tip — none can carry a sentinel distinguishable from data that legitimately belongs in the refs. Drafts were the only local-only surface holding user-authored text, so the invariant loses its only carrier along with the feature; no substitute test was written to keep a number up.
