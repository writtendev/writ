# Changelog

All notable changes to writ are documented in this file. The format is based
on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project
adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Each version's section is what GitHub publishes as that release's body.

## [Unreleased]

### Fixed
- `writ.schema` field names and `target(...)` arguments can now be `description`, `target`, `type`, `namespace`, `op`, `key`, and `untyped` (WRIT-204). All eight structural words used to be reserved everywhere, which made close to unexpressable a schema declaring fields the wire body already permits — `description` and `target` in particular are ordinary field names any vocabulary is likely to want. Reservation is now positional (`spec/schema-source.md` §2): a namespace, type name, or op type name still reserves all eight, but a field name or `target(...)` argument reserves only `deprecated`, whose modifier is bare and so cannot be told apart from a following field's own name with the one token of lookahead that disambiguates the other seven (`engine/schemasrc/parse.go`'s `validateName`, `parseOpBlock`'s description branch, and `parseField`'s `key`/`target` modifier handling; mirrored in `render.go`'s `validateNameForRender` so `Render` and `Parse` stay exact inverses). `engine/schemasrc/testdata/valid/contextual-keywords.schema` is the new positive fixture; `testdata/invalid/deprecated-field-name.schema` and `reserved-type-name.schema` pin the two reservations that remain.
- Colliding `TargetKey()`s in the review and issue rule tables merging assignees, labels, and ci-status/approval revisions under the generic fold (WRIT-198). `assign.add`/`assign.remove` and `label.add`/`label.remove` had no declared `target`, so both pairs fell back to the shared body field names `add`/`remove` — the generic fold (`writ.Fold`, `spec.Fold`) put review and issue assignees and labels into the same accumulator, and a `label.add` rule from one vocabulary could match another vocabulary's `label` op with no object-type check to stop it. Each OR-set pair now collapses onto one target instead — `assignees` and `labels` — following the `project`/`cycle` `add-issue.issue`/`remove-issue.issue` precedent; `review-ops`'s `ci-status.revision` now targets `ci_revision` (the `ci_description` precedent already on the same rule block), since it collided with `approval.revision` on differently-keyed tuples. Rule matching (`opMatchesRule`, both `engine/internal/fold` and `spec/reffold.go`) now also requires the op's and rule's object types to agree when both are declared, mirroring how a zero `op_version` on either side already matches anything; `spec.FieldRule` gains a derived, unserialized `ObjectType`, resolved per `field-rules.json` directory against a private `spec.vocabularyObjectTypes` map (exposed read-only via the copy-returning `spec.VocabularyObjectTypes()`) — `spec.FieldRules` now fails closed, naming the directory, when one has no entry in that map (rather than deriving an empty `ObjectType`, which matches every object type) and rejects two directories mapped to the same object type — and log-resolved rules (`RulesFromSchemas`) set it from the schema type name. The target-collision check (`schemasrc.checkTargetCollision`, `RulesFromSchemas`, and a new `spec.CheckTargetCollision` used by `spec.FieldRules` itself) now requires rules sharing a target to agree on `value_type`, `key`, `key_types`, `enum`, `max_length`, and `lattice`, not only `strategy` — with a carve-out for an `op_version` bump of the same `(op_type, field)`, which `spec/fold.md` §5 and `spec/schema-ops.md` §8 permit to change every attribute but `strategy` and `lattice`: `lattice`, unlike the other five, is consulted by the `lattice` accumulator at fold time, so two same-strategy `lattice` rules sharing a target but declaring different orderings are exactly as order-dependent — version bump or not — as two rules disagreeing on `strategy` itself, the same WRIT-186 hazard this check exists to close. `state.Rule` (and `writ.Rule`) gains an `ObjectType` field, left empty on every hand-written Go rule table (`ReviewRules`, `IssueRules`, etc. — WRIT-195 deleted them). Seven conformance goldens move; an eighth moves for the updated collision-error wording, and a new `schema-driven-cross-op-type-lattice-collision` fixture pins the `lattice` case.
- `CheckTargetCollision`'s `op_version`-bump carve-out (WRIT-198) defeating its own `lattice` exclusion (WRIT-206). The carve-out `continue`d past `equalMergeAttrs` entirely for a version-bump pair, so `lattice` — the one attribute `spec/schema-ops.md` §8 already excluded from the "MAY freely change" list, because the `lattice` accumulator reads it at fold time — was in practice also freely changeable under a version bump, the same order-dependence hazard the check exists to close. `equalMergeAttrs` (`spec/fieldrules.go`) now takes a `versionBump` flag and always checks `Lattice` regardless of it, skipping only the five genuinely freely-changeable attributes when the pair is a version bump; `CheckTargetCollision`'s error now names `lattice` specifically for a version-bump pair instead of folding it into the generic "every merge attribute" message. `spec/schema-ops.md` §8 is amended to state the rule; `spec/fold.md` §5 — the rule's other normative statement, which said the opposite ("MUST declare a distinct `target` only if the bump also changes `strategy`") — and `ARCHITECTURE.md` are corrected to match, and `spec/README.md`'s `schema-driven` fixture-family inventory gains the new fixture. `spec/fixtures/testdata/descriptions/schema-driven-version-bump-lattice-collision.yaml` (and a new `fieldrules_test.go` case) pin the version-bump half of the standard `schema-driven-cross-op-type-lattice-collision` already pinned for the cross-op-type half.

### Added
- `Store.Objects` (WRIT-192): a generic, schema-shaped replacement surface for the typed per-type write/read services, additive alongside them (they still ship; `cmd/writ` still calls them, and WRIT-195 deletes them once WRIT-193 re-points the CLI). `Objects.Create(ctx, objectType, op)` and `Objects.Apply(ctx, objectID, op)` take a `writ.NewOp{Type, Version, Fields}` — `Version` 0 resolves the op's version from `Store.Types` when the (object type, op type) pair is unambiguous, and both run no bespoke body validation, relying entirely on `dagStore.Append`'s existing producer validation (WRIT-188); `Objects.Create` no longer assumes op type `"create"` — a log-declared type may name its creating op anything (`spec/op-envelope.md` gives `create` only as an example). `Objects.Get(ctx, objectID)` folds directly from the DAG (`dagStore.Enumerate` + `state.Fold`), never the projection — the same precedent `Store.Schema` already set, for the same reason: the projection is a droppable cache, and Get returns identical `Object.Fields` before and after `Store.Rebuild` or an outright-deleted cache file. The returned `Object{ObjectID, ObjectType, Fields, UnknownOps}` deliberately omits `ObjectState.TotalOrder` (an `OpRef.Commit` is the op commit's SHA, and a caller supplying only an object id never asked for one); `Object.Fields` is keyed by TARGET key, which is not always the field name `NewOp.Fields` wrote it under — `assign.add`/`assign.remove` both write `add`/`remove` and both read back under `assignees` (WRIT-198). `Store.Types(ctx)` (new) returns the vocabulary actually in effect right now — built-in types overlaid by whatever the log declares, log wins per type — as opposed to `Store.Schema`, which returns only the `schema` objects present in the log and so is empty on a repository that has never run `writ schema apply`. `Query.Objects`' cross-type SQL (`engine/projection/query.go`) is now generated from the installed schema descriptor instead of five hard-coded built-in table/column literals (`review`, `issue`, `comment`, `project`, `cycle`): its full-text search becomes one `EXISTS` per declared type over that type's own `string`/`text` scalar columns, and its default not-deleted filter becomes "no `tombstone`-strategy target folded true" over every declared type that has one — so a log schema redeclaring any of those five types no longer bricks `Query.Objects` with a raw SQLite "no such column" (`(*DB).requireBuiltinShape`'s guard and `objectsHardcodedTypes` are gone from `Objects` entirely; every other typed reader in `query.go` keeps the guard, since the CLI still depends on them until WRIT-195). `checkBeforeAppend` moves from `engine/reviews.go` to `engine/schema.go`, next to `Store.ApplySchema`, the surviving caller WRIT-195 must not take down when it deletes `reviews.go`.
- `writ object create|apply|show|list` and `writ schema show` (WRIT-193): generic CLI porcelain over `Store.Objects`/`Store.Query.Objects`/`Store.Types` (WRIT-192), additive alongside the existing per-type commands (`writ review`, `writ issue`, `writ comment`, `writ label`, `writ settings`, `writ state`), which keep working until WRIT-195 deletes them. `object create <type> <op-type>` and `object apply <object-id> <op-type>` take repeatable `-field <k>=<v>` flags, looked up against the installed vocabulary's field rules and parsed by each field's declared value type (`int`/`number`/`bool` parsed accordingly, `anchor` as a JSON object, everything else passed through as a string) — a bad value is refused at the CLI naming the field and its declared value type, while enum membership, `max_length`, and pattern checks stay with the producer validator that already runs. The same `-field k=` given more than once builds a JSON array instead of a scalar. `object show` folds an object directly from the log (never the projection); `object list` filters and pages across or within one type from the projection cache. `schema show [<type>]` reports `Store.Types` — the vocabulary installed and folding right now, distinct from what `schema plan`/`apply` compute from the working-tree file — printing one bare type name per line with no argument, or one type's ops and fields with one. All five support `--json` (`object.create`, `object.apply`, `object.show`, `object.list`, `schema.show` in `docs/cli-json.md`); `object.show`'s `fields` is an open map keyed by target key, the one place this CLI's JSON payloads carry a schema-shaped field set rather than a fixed one. `parseArgs`/`stringSliceFlag` move from `cmd/writ/review.go` to a neutral `cmd/writ/args.go`, and `cmd/writ/store.go` gains `resolveObjectID` alongside the existing per-type id resolvers.
- `writ schema plan` and `writ schema apply` (WRIT-191): the workflow connecting the `writ.schema` working-tree source file to the schema objects in the log. `plan` parses the file, folds the schema objects in the repository, and prints the ops applying it would append (appends no ops itself); `apply` runs the same computation and signs and appends the result. Which schema object `apply` writes to is resolved fresh on every run by matching the file's namespace against the folded log — reusing an existing match, minting a fresh object id only when the repository has none, and refusing outright (on the reuse path too) when the file would bind an `object_type` another schema object already binds, since that collision makes `RulesFromSchemas` withhold every rule for the contested type, permanently; when every contested type traces to one existing object, the refusal reads as the namespace change it is. `plan` also refuses any edit that would remove a declaration (a type, op, field, or description; an un-deprecation) or that would narrow a field's `value_type`, `enum`, `max_length`, `lattice`, `key`, `key_types`, or `target` — state.FoldSchema's define-field case overwrites each of those independently, only when a later op's body still carries it, so a narrowing op would leave the log holding the old attribute forever with no way to clear it — since nothing is ever removed from the log. `plan --json` omits `object_id` on a creation plan — there is no id yet for a later `apply` to be bound to. Adds `Store.ApplySchema`, the pure `SchemaFromEnvelopes`, and `Store.SchemaAfterApply` (folds an object's real log history together with a proposed delta, so a conflict check sees the schema state a real apply would actually produce, not the state folding the file alone produces) to the engine's public API. `writ init` now writes a starter `writ.schema` (a namespace line, no types) for any repository with a working tree that doesn't already have one.
- Document collaborative object type (`document` and `section`), multi-value fold register strategy, fractional section ordering, and CLI porcelain (`writ doc`).
- Carried `object_type` in `writ.UnknownOp`, `state.UnknownOp`, CLI JSON output, and SQLite projection cache to satisfy forward-compatibility rule `FC-5`.
- Value types (WRIT-185): a closed catalogue of 12, orthogonal to the merge-strategy catalogue, specified in the new normative `spec/value-types.md` and `spec/schemas/value-types.schema.json`. `spec.FieldRule` / `state.Rule` / `writ.Rule` gain `ValueType`, `Enum`, `MaxLength`, and `KeyTypes`; all ten shipped `field-rules.json` tables now declare a value type per field (one rule, `comment.create.subject`, is deliberately untyped). Producer validation (`engine/codec`) rejects a value that fails its declared type, via the new pure leaf package `engine/internal/value`. `spec/vocabulary.go`'s schema-enum scraping is replaced by a lookup over the folded rule tables (`spec.EnumValues`).
- `codec.Vocabulary` / `codec.Vocabularies` / `codec.OpVersionKey` and `writ.VocabulariesFromSchemas` (WRIT-188): producer validation now drives off the `schema` object in the log, not only a hand-written Go table. `spec/op-envelope.md` §Producer validation's rules 3 and 4 resolve "the schema object governing `object_type`" through a five-tier precedence — `schema` itself always against the engine's built-in bootstrap table; otherwise a log-declared, uncontested type against the schema that declares it (exclusively — it is never merged with the embedded table for the same type); otherwise, for now, the ten still-embedded SDLC vocabularies (deleted by WRIT-194); otherwise, if the type is *contested* (two or more schema objects bind the same bare `object_type`, spec/schema-ops.md §6), the write is permitted unvalidated rather than refused — refusing would be a *permanent* write outage, since nothing is ever removed from the log and a contested type is contested forever (deleted by WRIT-199, the moment that race has an answer); otherwise the write is refused, naming the `object_type`. Required fields are deliberately not checked: the schema DSL has no requiredness to check against. `spec/testdata/producer/` is the new conformance corpus, pinning both the producer's verdict and a reader's disposition over the identical op for nine cases covering tiers 2, 4, and 5 (tiers 1 and 3 are covered in Go instead, by `TestSchemaObjectAlwaysValidatesAgainstBootstrapTable` and `TestLogSchemaSupersedesEmbeddedVocabulary`).

### Changed
- The SQLite projection's per-type tables are now generated from the folded schema instead of hand-written (WRIT-189). `engine/projection/ddl.go` turns a rule index (`RulesFromSchemas`' shape — the built-in vocabulary overlaid by whatever the log declares, log wins per type) into a descriptor: one `o_<type>` table per declared object type with a `f_<target>` column per scalar target, a child table per collection or keyed-lww-key-tuple group, and a SHA-256 digest over its canonical JSON. `projection.DB.ApplySchema(rules)` (new) reconciles that descriptor against whatever tables exist on disk — a matching digest is a no-op, a different one drops the previously-generated tables, emits the new DDL, truncates `anchor_resolutions`, and marks the cache for a full rebuild on the next `Refresh` — the droppable-cache answer (drop and rebuild, never migrate) applied to a schema change instead of only a rewound ref tip. `projection.WithSchema` (new `Option`) supplies the rule index to `Refresh`/`Rebuild`; `engine.Store` resolves it (built-ins from `spec.FieldRules()` overlaid by `RulesFromSchemas`, memoised behind the same `dag.Chains` fingerprint `Store.vocabularies` already uses) and applies it on every `Refresh`/`Rebuild`, plus once at `Open` — but only when the reopened cache has no generated tables yet (`!HasGeneratedTables()`): a reopened cache already has its tables, correctly shaped for whatever schema last applied, so `Open` skips the resolve on a warm cache and leaves a real schema change since to be caught lazily by the first `Refresh`/`Rebuild` that runs, the same way any other log change is. The materializer (`materialize.go`) no longer switches on a Go type name: it folds every declared object's ops generically (`state.Fold`) and writes whatever the descriptor says, including a generic `unknown_fields` column (the same forward-compatibility semantics `settings.UnknownKeys` had, generalized) and a single derived helper for the three position-tracking `*_op_id` columns that used to be hand-written per type. An untyped scalar target's raw JSON bytes (`comment.create.subject` is the one case in the shipped vocabulary) get a generic `__members` child table, one row per top-level key, indexed on `(member, value)`, so a filter on it stays indexed instead of falling back to an unindexed `json_extract` scan — `Comments`' subject filtering is re-pointed at it. `anchor_resolutions` is generalized from a hard-coded read of `comments.anchor` to every column whose declared `value_type` is `"anchor"`, and its key column is renamed `comment_object_id` → `object_id` with a new `target` column, so a second anchor-valued target would resolve into distinguishable rows. An object whose type is undeclared, withheld (an invalid target or keyed-lww key-component identifier), or removed from a later schema falls through to `unknown_ops` exactly as an absent schema always has — nothing in the log is lost. `schemaVersion` (substrate shape) and the descriptor digest (generated-table shape) are now two independent invalidation keys; `schemaVersion` is bumped 14 → 15 for the removed hand-written tables. Every hand-written typed reader in `engine/projection/query.go` — `Reviews`/`Review`, `Issues`/`Issue`, `Comments`, `Threads`, `GroupIssues`, the workflow-state/label/document/section/settings readers, and the cross-type `Objects` summary query — now refuses with a named `projection: object type %q was redeclared by a log-declared schema` error instead of failing on a raw SQLite "no such column" once a log-declared schema has reshaped a built-in type's generated table out from under that reader's hard-coded SQL (`(*DB).requireBuiltinShape`, compared against a reference shape computed once from `state.BuiltinRules()`); the generic, schema-agnostic `Object` (singular) API is unaffected, since it hard-codes no built-in column. `state.BuiltinRules` (new, public, guarded by `api/engine.txt`) is the one shared construction of "the built-in vocabulary's fold rules, grouped by object type" that `engine.Store`'s own resolver and every projection test now delegate to, replacing four copies that used to drift independently. No spec text or conformance fixture changes: the projection's DDL is not the wire format, the op envelope, canonical encoding, or fold behaviour.
- `codec.BuildCommit` and `codec.ValidateBody` (WRIT-188, breaking, pre-v0.1.0) each take a new `codec.Vocabularies` parameter — the log-sourced producer declarations described above; `nil` is legal and means the log declares nothing. `dag.Store` gains `dag.WithProducerVocabularies`, resolved once per `Append` (before its CAS retry loop, not once per `BuildCommit`) rather than once per attempt. `engine.Store` installs a resolver memoised behind a fingerprint over its discovered chains (`dag.Chains`), reused by both `Append` and the multi-append guard `checkBeforeAppend` (now a `*Store` method, with two callers: `Reviews.Create` and `Store.ApplySchema`) so neither can see a different view of the schema than the other. `dag.Store` also gains `dag.WithChainObserver`, which `engine.Store` wires to roll that fingerprint's cached snapshot forward after each of its own local appends (`Store.noteAppend`) instead of re-deriving it from a fresh `dag.Chains` pass on every single `Append` — a `"schema"` append instead drops the cached snapshot outright, since it is exactly the kind of append that can change what the log resolves to, and the next resolve pays for a real re-derivation. `dag.Chains` itself is unchanged, still a single `IterReferences` pass over every reference in the repository; a cache miss's cost is therefore still linear in the repository's total ref count, not only its writ chain count. A directory-scoped fast path was tried and reverted during review: it could fail every `Append` and `Enumerate` outright when a remote happened to have a branch named `writ`, and it silently dropped chains fetched from a slash-named remote. The underlying per-append cost is tracked as its own follow-up ticket rather than fixed here.

### Removed
- The SDLC vocabulary, deleted from the spec in full (WRIT-194, breaking, pre-v0.1.0). Writ now knows exactly one object type, `schema`; every other type is declared as data by a consumer's schema written into the log, the way git knows nothing about GitHub. Nothing has shipped (`AGENTS.md`), so this is a deletion rather than a deprecation: no tolerance shim, no migration path, and no fixture pinning a form the format never released. The design thinking behind the deleted vocabularies is preserved outside this repository.
  - Prose: `spec/review-ops.md`, `spec/issue-ops.md`, `spec/project-cycle.md`, `spec/comments.md`, `spec/documents.md`, `spec/label-ops.md`, `spec/workflow-state-ops.md`, `spec/settings-ops.md`.
  - JSON schemas: `review-ops`, `comment`, `issue-ops`, `project-ops`, `cycle-ops`, `document-ops`, `label-ops`, `workflow-state-ops`, `settings-ops`. What remains under `spec/schemas/` is the substrate — `op-envelope`, `anchor`, `identifiers`, `ordering`, `value-types`, `resolution`, `field-rules` — plus `schema-ops`.
  - Conformance corpora: every `spec/testdata/<vocabulary>/` directory and every `field-rules.json` except `spec/testdata/schema-ops/field-rules.json`, the bootstrap table that never comes from the log. The signed-fixture families carrying those vocabularies go with them; the substrate families they used to ride on — deterministic total order, equal-`t*` tiebreak, fractional ordering, multi-device chains, truncated ancestry, person-identifier schemes and Unicode folding, empty set items — are re-carriered onto schema-declared types and keep their coverage. `spec/testdata/forward-compat/`'s synthetic reader profile now states its own merge rules inline instead of naming a shipped vocabulary directory, so forward compatibility is pinned against a reader whose log declared its types, which is what every reader now is.
  - `spec/vocabulary.go` in full, and with it `spec.VocabularyObjectTypes`, `spec.EnumValues`, `spec.ReviewStatuses`, `spec.ApprovalVerdicts`, `spec.CIStatusStates`, `spec.LinkRelations`, `spec.ProjectStatuses`, `spec.WorkflowStateTypes`, `spec.EstimateScales`, `spec.FormatOptions`, `spec.IssuePriorityNames`, `spec.ParseIssuePriority`, and `spec.FormatIssuePriority`.
  - `state.BuiltinRules`, and the built-in-vocabulary half of the engine that consumed it: `Store.Types` now returns exactly what the log declares (nothing, on a repository with no schema objects) rather than shipped types overlaid by the log, and `Store.rules` is `RulesFromSchemas` alone.
  - Tier 3 of `spec/op-envelope.md` §Producer validation — "the producer still embeds a hand-written vocabulary for `object_type`" — leaving a four-tier precedence: `schema` against the bootstrap table, else the log's uncontested declaration, else a contested type permitted unvalidated (WRIT-199 deletes that one), else refusal. `engine/codec`'s `vocabularySchemaFiles`, `vocabularyOpTypes` and `fieldRuleVocabularies` each hold one entry now, for `schema`.
  - Forward compatibility is unchanged and stays: ops of the deleted types are now simply ops of unknown types, and a reader still preserves them and their unknown fields intact rather than dropping them.
- The seven per-type engine services, their typed `Query` readers, and the seven per-type CLI command families (WRIT-195, breaking, pre-v0.1.0 — the largest single API surface reduction to date, `api/engine.txt` shrinking by well over half). Nothing has shipped yet (`AGENTS.md`), so this is a deliberate pre-v0.1.0 break with no tolerance shim or migration path: the replacement is `Store.Objects`/`Store.Query.Objects`/`Store.Types` (WRIT-192) and `writ object`/`writ schema show` (WRIT-193), which every deleted call site above already had a generic equivalent for. `checkBeforeAppend`'s log-vocabulary branch and its `needsLogVocabularies` helper go with them: `Store.ApplySchema` is the only remaining caller and always passes `schema` envelopes, for which `codec.ValidateBody` ignores vocabularies unconditionally, so the branch had no reachable production path.
  - `Store.Reviews`, `.Issues`, `.Comments`, `.WorkflowStates`, `.Labels`, `.Documents`, `.Settings` and every type in their signatures (`NewReview`, `ReviewEdit`, `ReviewStatus`, `NewIssue`, `IssueEdit`, `IssueState`, `NewComment`, `CommentResolve`, and the rest).
  - `Query.Reviews`/`.Review`, `.Issues`/`.Issue`, `.Comments`, `.Threads`, `.WorkflowStates`/`.WorkflowState`, `.Labels`/`.Label`, `.Documents`/`.Document`/`.Section`, `.Settings`, and their filter/result aliases (`ReviewFilter`, `ReviewResult`, `IssueFilter`, `IssueResult`, `CommentFilter`, `CommentResult`, `WorkflowStateFilter`, `WorkflowStateResult`, `LabelFilter`, `LabelResult`, `DocumentFilter`, `DocumentResult`, `SectionResult`, `SettingsResult`) and `ResolvedPosition`.
  - The eight non-time `OrderBy` constants (`OrderByTitleAsc`/`Desc`, `OrderByPriorityAsc`/`Desc`, `OrderByPositionAsc`/`Desc`, `OrderByEstimateAsc`/`Desc`) — `DB.Objects` only ever honoured the four created/updated orderings, so these were already unreachable through the surviving surface.
  - `FoldReview`, `FoldComment`, `FoldComments`, `FoldIssue`, `FoldProject`, `FoldCycle`, `FoldWorkflowState`, `FoldLabel`, `FoldSettings`, `FoldDocument`, `FoldSection` and `ReviewRules`, `IssueRules`, `ProjectRules`, `CycleRules`, `WorkflowStateRules`, `LabelRules`, `SettingsRules`, `DocumentRules`, `SectionRules` (`FoldSchema`/`SchemaRules` stay — schema folding never came from a per-type table).
  - Every per-type alias in the root package — `Review`, `Revision`, `Approval`, `CIStatus`, `Comment`, `CommentSubject`, `CommentThread`, `Issue`, `Link`, `Project`, `Cycle`, `WorkflowState`, `Label`, `Document`, `Section` — plus `ParseCommentSubject`, `DefaultSettings`, `DefaultSettingsObjectID`.
  - `engine/projection`'s typed readers and result types (the same set `Query` re-exported above), `engine/projection/typed_reader_guard.go`'s `requireBuiltinShape` guard, and the five per-type `Filter` types in `engine/projection/filter.go`.
  - `engine/guards.go` (`requireCommitOID`, `validateLabels`, `validateAnchor`) — its ten call sites were all in the deleted `reviews.go`/`issues.go`.
  - `writ review`, `writ issue`, `writ comment`, `writ label`, `writ settings`, `writ state`, and `writ doc` (each now exits 2 with `writ: unknown command`), their `--json` kinds (`review.list`, `review.status`, `issue.list`, `issue.status`, `issue.label`, `comment.edit`, `comment.delete`, `state.list`, `label.list`, `doc.*`, `settings`) and wire types, and their generated goldens.
  - **Known consequence, not fixed here:** `Query.Comments` was the only public reader of the `anchor_resolutions` table. The table is still generated and materialized generically from every `anchor`-valued target (WRIT-189) and is still covered by `engine/projection/anchors_test.go` via raw SQL, but no public API returns a resolution any more — `writ object show` carries an anchor through as opaque JSON. A generic resolution reader is deferred until a real consumer needs one, tracked as a follow-up rather than built speculatively here.
  - **Known consequence, not fixed here:** `Drafts.Publish` (the generic replacement for the deleted type-specific comment writers) no longer threads a comment's subject/reply frontier in as its causal DAG parents. `Objects.Create` has no parameter for observed causal parents, so a comment on an object written by another writer is no longer kept reachable by that comment once its origin ref rolls back or is only partially fetched (ARCHITECTURE.md §Ref layout, spec/ref-layout.md §Producer requirements). This is a cross-object causal edge only — the cross-writer, intra-object edges `Objects.Apply` and `ApplySchema` emit at `parents[1:]` are unaffected. See `engine/drafts.go`'s `Publish` doc comment for the full account.
- `Query.GroupIssues`, `writ.Group`, `writ.GroupKey`, `writ.GroupByState`/`GroupByAssignee`/`GroupByPriority`, and `projection.DB.GroupIssues`/`Group`/`GroupKey`/the same three constants/`engine/projection/group.go` (WRIT-192, breaking, pre-v0.1.0): typed-issue-only grouping machinery with no production consumer — its own tests were the only caller — dropped as part of replacing the typed services with the schema-shaped `Store.Objects` surface above, rather than carried into WRIT-195's larger deletion.
- `writ.NormalizeRule` and `state.NormalizeRule` (WRIT-185): normalization is no longer a separate rule attribute. It is now intrinsic to the `person-ref` value type — `Rule.Normalize` is gone, replaced by `ValueType`/`KeyTypes`, and `FieldRule.NormalizesValue`/`NormalizesItems`/`NormalizesKey` keep their old signatures and results, deriving them from `value_type == "person-ref"` instead.
- Workspace routing (WRIT-180): `writ.Workspace`, `writ.WorkspaceInfo`, `WithWorkspace`, `writ.ResolveReference`, `writ.ResolvedReference`, `ErrWorkspaceRemoteURLNotSupported`, and `ErrWorkspaceUnconfigured` are gone from the engine's public API, along with the `writ.workspace` git config key and `writ init`'s workspace auto-registration. Every collaborative object now homes in the repo writ was opened on; there is no configured elsewhere and no routing branch. Qualified references (`<repo-id>#<object-id>`) still parse via `writ.ParseReference`, but resolving one against a repository other than the one writ is standing in is a job for a higher layer now.
- The `repo` collaborative object type (WRIT-182): `writ.RepoEntry`, `writ.FoldRepo`, `writ.RepoRules`, `state.ResolveReference`, `state.ResolvedReference`, `state.RepoEntry`, `state.FoldRepo`, `state.RepoRules`, and `projection.DB.Repo`/`DB.Repos` are gone, along with the `repos`/`repo_remotes` projection tables (`schemaVersion` bumped 13 → 14, so an existing `.writ` cache rebuilds automatically). The repository registry it modeled — mapping a repo-id to a slug, remote URLs, and workspace membership — was resolution machinery that WRIT-180 already moved out of writ's scope; `<repo-id>#<object-id>` stays representable as an opaque reference via `writ.ParseReference`.
