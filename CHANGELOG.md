## [Unreleased]

### Fixed
- Colliding `TargetKey()`s in the review and issue rule tables merging assignees, labels, and ci-status/approval revisions under the generic fold (WRIT-198). `assign.add`/`assign.remove` and `label.add`/`label.remove` had no declared `target`, so both pairs fell back to the shared body field names `add`/`remove` — the generic fold (`writ.Fold`, `spec.Fold`) put review and issue assignees and labels into the same accumulator, and a `label.add` rule from one vocabulary could match another vocabulary's `label` op with no object-type check to stop it. Each OR-set pair now collapses onto one target instead — `assignees` and `labels` — following the `project`/`cycle` `add-issue.issue`/`remove-issue.issue` precedent; `review-ops`'s `ci-status.revision` now targets `ci_revision` (the `ci_description` precedent already on the same rule block), since it collided with `approval.revision` on differently-keyed tuples. Rule matching (`opMatchesRule`, both `engine/internal/fold` and `spec/reffold.go`) now also requires the op's and rule's object types to agree when both are declared, mirroring how a zero `op_version` on either side already matches anything; `spec.FieldRule` gains a derived, unserialized `ObjectType`, resolved per `field-rules.json` directory against a private `spec.vocabularyObjectTypes` map (exposed read-only via the copy-returning `spec.VocabularyObjectTypes()`) — `spec.FieldRules` now fails closed, naming the directory, when one has no entry in that map (rather than deriving an empty `ObjectType`, which matches every object type) and rejects two directories mapped to the same object type — and log-resolved rules (`RulesFromSchemas`) set it from the schema type name. The target-collision check (`schemasrc.checkTargetCollision`, `RulesFromSchemas`, and a new `spec.CheckTargetCollision` used by `spec.FieldRules` itself) now requires rules sharing a target to agree on `value_type`, `key`, `key_types`, `enum`, `max_length`, and `lattice`, not only `strategy` — with a carve-out for an `op_version` bump of the same `(op_type, field)`, which `spec/fold.md` §5 and `spec/schema-ops.md` §8 already permit to change every attribute but strategy. `lattice` is excluded from that carve-out's freely-changeable set because, unlike the other five, it is consulted by the `lattice` accumulator at fold time; two same-strategy `lattice` rules sharing a target but declaring different orderings previously passed with zero diagnostics and made folded state depend on rule-slice order, the same WRIT-186 hazard this check exists to close. `state.Rule` (and `writ.Rule`) gains an `ObjectType` field, left empty on every hand-written Go rule table (`ReviewRules`, `IssueRules`, etc. — WRIT-194 deletes them). Seven conformance goldens move; an eighth moves for the updated collision-error wording, and a new `schema-driven-cross-op-type-lattice-collision` fixture pins the `lattice` case.

### Added
- `writ schema plan` and `writ schema apply` (WRIT-191): the workflow connecting the `writ.schema` working-tree source file to the schema objects in the log. `plan` parses the file, folds the schema objects in the repository, and prints the ops applying it would append (appends no ops itself); `apply` runs the same computation and signs and appends the result. Which schema object `apply` writes to is resolved fresh on every run by matching the file's namespace against the folded log — reusing an existing match, minting a fresh object id only when the repository has none, and refusing outright (on the reuse path too) when the file would bind an `object_type` another schema object already binds, since that collision makes `RulesFromSchemas` withhold every rule for the contested type, permanently; when every contested type traces to one existing object, the refusal reads as the namespace change it is. `plan` also refuses any edit that would remove a declaration (a type, op, field, or description; an un-deprecation) or that would narrow a field's `value_type`, `enum`, `max_length`, `lattice`, `key`, `key_types`, or `target` — state.FoldSchema's define-field case overwrites each of those independently, only when a later op's body still carries it, so a narrowing op would leave the log holding the old attribute forever with no way to clear it — since nothing is ever removed from the log. `plan --json` omits `object_id` on a creation plan — there is no id yet for a later `apply` to be bound to. Adds `Store.ApplySchema`, the pure `SchemaFromEnvelopes`, and `Store.SchemaAfterApply` (folds an object's real log history together with a proposed delta, so a conflict check sees the schema state a real apply would actually produce, not the state folding the file alone produces) to the engine's public API. `writ init` now writes a starter `writ.schema` (a namespace line, no types) for any repository with a working tree that doesn't already have one.
- Document collaborative object type (`document` and `section`), multi-value fold register strategy, fractional section ordering, and CLI porcelain (`writ doc`).
- Carried `object_type` in `writ.UnknownOp`, `state.UnknownOp`, CLI JSON output, and SQLite projection cache to satisfy forward-compatibility rule `FC-5`.
- Value types (WRIT-185): a closed catalogue of 12, orthogonal to the merge-strategy catalogue, specified in the new normative `spec/value-types.md` and `spec/schemas/value-types.schema.json`. `spec.FieldRule` / `state.Rule` / `writ.Rule` gain `ValueType`, `Enum`, `MaxLength`, and `KeyTypes`; all ten shipped `field-rules.json` tables now declare a value type per field (one rule, `comment.create.subject`, is deliberately untyped). Producer validation (`engine/codec`) rejects a value that fails its declared type, via the new pure leaf package `engine/internal/value`. `spec/vocabulary.go`'s schema-enum scraping is replaced by a lookup over the folded rule tables (`spec.EnumValues`).

### Removed
- `writ.NormalizeRule` and `state.NormalizeRule` (WRIT-185): normalization is no longer a separate rule attribute. It is now intrinsic to the `person-ref` value type — `Rule.Normalize` is gone, replaced by `ValueType`/`KeyTypes`, and `FieldRule.NormalizesValue`/`NormalizesItems`/`NormalizesKey` keep their old signatures and results, deriving them from `value_type == "person-ref"` instead.
- Workspace routing (WRIT-180): `writ.Workspace`, `writ.WorkspaceInfo`, `WithWorkspace`, `writ.ResolveReference`, `writ.ResolvedReference`, `ErrWorkspaceRemoteURLNotSupported`, and `ErrWorkspaceUnconfigured` are gone from the engine's public API, along with the `writ.workspace` git config key and `writ init`'s workspace auto-registration. Every collaborative object now homes in the repo writ was opened on; there is no configured elsewhere and no routing branch. Qualified references (`<repo-id>#<object-id>`) still parse via `writ.ParseReference`, but resolving one against a repository other than the one writ is standing in is a job for a higher layer now.
- The `repo` collaborative object type (WRIT-182): `writ.RepoEntry`, `writ.FoldRepo`, `writ.RepoRules`, `state.ResolveReference`, `state.ResolvedReference`, `state.RepoEntry`, `state.FoldRepo`, `state.RepoRules`, and `projection.DB.Repo`/`DB.Repos` are gone, along with the `repos`/`repo_remotes` projection tables (`schemaVersion` bumped 13 → 14, so an existing `.writ` cache rebuilds automatically). The repository registry it modeled — mapping a repo-id to a slug, remote URLs, and workspace membership — was resolution machinery that WRIT-180 already moved out of writ's scope; `<repo-id>#<object-id>` stays representable as an opaque reference via `writ.ParseReference`.
